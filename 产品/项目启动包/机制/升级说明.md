# 升级说明：已接入的项目换成新版启动包

给 Agent 看。用户会把新版的整个 `项目启动包/` 文件夹复制到项目根目录，然后说「按 `项目启动包/机制/升级说明.md` 升级这个项目」。下面的「启动包」都指这个新复制进来的文件夹。

## 升级什么，不动什么

| 内容 | 怎么处理 |
|---|---|
| `AGENTS.md` 的「工作机制」一节 | 整节替换成新版 |
| `机制/` 文件夹 | 用新版替换 |
| `AGENTS.md` 的「本项目」一节 | **不动** |
| `沉淀/`、`进度.md` | **不动**。新版改了沉淀的规则时，按第 6 步提议整理，用户同意才改 |
| `CLAUDE.md` | 确认只有一行 `@AGENTS.md`，不是的话告诉用户 |
| 产出（草稿、成品、素材、代码等） | **不动** |

## 步骤

### 1. 看版本

- 读项目 `AGENTS.md` 里「工作机制」一节标题上的版本号。标题里没有版本号的，按 v1.0 处理。
- 读启动包 `AGENTS.md` 里的版本号。
- 两边一样的话，告诉用户已经是最新版，把启动包文件夹删掉，到此结束。

### 2. 告诉用户变了什么，等确认

- 对比两边「工作机制」一节的差别，用几句大白话告诉用户：新版新增了什么、改了什么、删了什么。
- 检查「本项目」一节里有没有和新版「工作机制」冲突的地方。有的话单独列出来，问用户怎么处理。按「本项目优先」的规则，冲突时默认保留「本项目」的写法；但新版里标了「不可覆盖」的条款，一律以新版为准。
- **用户确认之前，什么都不改。**

### 3. 备份

把项目现有的 `AGENTS.md`、`CLAUDE.md` 和 `机制/` 原样复制到 `_升级前/<今天日期>/`。

### 4. 替换

1. 把项目 `AGENTS.md` 里从「## 工作机制」开始一直到文件末尾的内容，换成启动包 `AGENTS.md` 里同样范围的内容，逐字复制。
2. 用启动包里的 `机制/` 替换项目里的 `机制/`。
3. 用户在第 2 步对冲突做了决定的，按决定修改「本项目」一节。改「本项目」前必须先问（不可覆盖）：第 2 步的确认就算问过了，没在第 2 步提到的地方不要改。
4. 把启动包文件夹移进 `_升级前/<今天日期>/`。

### 5. 自检和汇报

- 项目 `AGENTS.md` 的「工作机制」一节和启动包里的逐字相同。
- 「本项目」一节除了用户同意改的地方，和升级前一样。
- `沉淀/`、`进度.md` 和产出都没有被改动。

告诉用户：升到了哪个版本、改了什么、备份在哪里。

### 6. 按新规则检查已有内容（新版改了沉淀或流程规则时才做）

替换完成后，新规则只管以后。已有的 `沉淀/` 和「本项目」一节可能还留着不符合新规则的内容，要单独检查一次：

1. 按新版「工作机制」检查 `沉淀/` 里的每个文件和「本项目」一节，列一张表：哪一条、不符合新版哪条规则、建议怎么改（提炼成原则、合并进哪一条、改成例子、删掉）。
2. 「本项目」里有和新规则冲突的规定（比如要求 Agent 维护事件记录），也列进表里。
3. **用户确认之前，什么都不改**（不可覆盖）。用户可以只同意其中几条。
4. 改之前把要改的文件复制到 `_升级前/<今天日期>/`；改完告诉用户改了哪些。

最后建议用户新开一个对话，第一句问「你读到了哪些项目规约？」，确认新版已经生效。
