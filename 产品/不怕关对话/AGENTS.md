## 工作机制（通用部分 v1.3，各项目相同，不要删；升级时整节替换）

核心原则：项目的连续性靠文件，不靠对话。对话只做当前这一件事；值得留下的写进文件，然后对话就可以结束。

「本项目」一节和本节冲突时，以「本项目」为准，标了「不可覆盖」的除外。

**不可覆盖：写进 `AGENTS.md`、`CLAUDE.md` 或 `沉淀/` 之前，一定先问用户，用户同意后才写。** 任何项目都不能例外。

### 一、骨架和读文件

- 项目只用这几样：`AGENTS.md`（规约）、`CLAUDE.md`（只有一行 `@AGENTS.md`）、`沉淀/`、`进度.md`（做完的移到 `进度-已完成.md`）、`机制/`。其他文件夹按需要建。
- 规约只写流程和指引，要短。会过期的内容（做到哪一步、最新文件叫什么）放进 `进度.md`。
- 「本项目」还是模板占位符时，先和用户一起填好，再开始做事。
- **按需读**：读进对话的文件会一直占着额度。开工时只读「做事之前先读」里标「每次」的文件；其他文件，包括 `机制/` 里的说明，到了写明的场景再读，而且到了就一定要读。

### 二、对话管理

一个对话只做一件事。同一篇稿子、同一个功能、同一批 bug，算同一件事。要不要新开对话由 Agent 判断，不用用户操心。

- 用户提需求时，先判断是不是当前这件事的后续。是，就直接做。
- 是一件**不相关**的新事时，先引导：把还没写进文件的要点按第三节沉淀；告诉用户「这是另一件事，建议在新对话里做，需要的信息都已经在文件里了」；工具能新建对话的，问用户要不要帮他开，不能的，给一句可以直接粘贴的开场话。用户坚持在这里做，就照做。
- 新对话不需要交接文档。只有一件事做到一半必须换对话时，才把当前情况写进 `进度.md` 对应的条目。

### 三、沉淀

用户纠正、补充或做出选择，而且是「以后都要这样」（不只针对这一次）时，**当场**读 `机制/沉淀说明.md`，按它提议写进文件。

### 四、进度

用户提的事在当前回合做不完（交给别的 Agent 或队列、要等、分几步完成）时，读 `机制/进度说明.md`，按它建条目、改状态。`进度.md` 只放用户交代的、还没做完的事，不放事实、资料和规则候选。用户问「做到哪了」，读 `进度.md`，用一张简短的表回答。

### 五、收尾

任何任务最后都要验收，最终由用户确认。

- 用户用任何说法表示可以了（「行了」「通过」「定稿」等），就是确认。
- 用户没说，但满足任意一条时，Agent 要主动问：约定的验收标准都已满足、自查也通过；最新版已经交给用户，用户没有再提修改；`进度.md` 里的条目已经是「待你验收」。说出依据，问：「我看这件事已经可以验收了，你确认通过吗？」

用户确认后，读 `机制/收尾说明.md`，按顺序收尾。
