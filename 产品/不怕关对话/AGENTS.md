## 工作机制（通用部分 v1.2，各项目相同，不要删；升级时整节替换）

核心原则：项目的连续性靠文件，不靠对话。对话只用来做当前这一件事；值得留下的东西要写进文件，然后对话就可以结束。

「本项目」一节里的规定和本节冲突时，以「本项目」为准。标了「不可覆盖」的条款除外。

**不可覆盖：写进 `AGENTS.md`、`CLAUDE.md` 或 `沉淀/` 之前，一定先问用户，用户同意后才写。** 任何项目都不能例外。

### 一、项目骨架

- 项目只用这几样东西：`AGENTS.md`（规约）、`CLAUDE.md`（只有一行 `@AGENTS.md`）、`沉淀/`、`进度.md`、`机制/`。其他文件夹按项目需要建。
- 规约只写流程和指引，要短。不写会过期的内容，比如做到哪一步、最新文件叫什么，这些放进 `进度.md`。
- 「本项目」一节还是模板占位符时，先和用户一起把它填好，再开始做事。

### 二、对话管理

一个对话只做一件事。同一篇稿子、同一个功能、同一批 bug，算同一件事。用户不需要自己判断要不要新开对话，这由 Agent 负责。

- 每次用户提需求时，先判断它是不是当前这件事的后续。是，就直接做。
- 不是（一件**不相关**的新事）时，不要直接开做，先引导用户：
  1. 如果当前对话里有还没写进文件的要点，先按第三节沉淀。
  2. 告诉用户：「这是另一件事，建议在新对话里做，需要的信息都已经在文件里了。」
  3. 如果你所在的工具能直接新建对话或会话，就问用户要不要帮他开，并把这个需求带过去；如果不能，就给用户一句可以直接粘贴到新对话里的开场话，写清楚这个需求。
  4. 用户坚持在当前对话里做，就照做。
- 一件事做完时，按第五节收尾。
- 新开对话不需要交接文档：读规约、`沉淀/` 和 `进度.md` 就够了。只有一件事做到一半必须换对话时，才把它的当前情况写进 `进度.md` 对应的条目。

### 三、沉淀

用户纠正、补充或者做出选择时，判断这是「只针对这一次」还是「以后都要这样」：

| 类型 | 写到哪里 |
|---|---|
| 只针对这一次 | 不沉淀，在当前产出里改掉即可 |
| 以后的做事流程 | `AGENTS.md` 的「本项目」一节 |
| 以后不能怎样、必须怎样 | `沉淀/规则.md` |
| 风格、语气、偏好 | `沉淀/风格.md` |
| 否决了某个方案，以及原因 | `沉淀/规则.md` 里的「已否决」一节 |

**判断为「以后都要这样」后，提议之前按顺序想三步：**

1. **往上提炼**：这次纠正背后的通用原则是什么？要沉淀的是原则，不是这一个句子、这一个词。比如用户把一句病句改了，原则可能是「交稿前通读一遍」，而不是「这句不要这样写」。
2. **查现有条目**：现有规则或流程已经覆盖了这个原则，就说明是没执行，不新加条目。可以做的是：在原条目下补一个例子；或者问题出在漏了自查，就在「本项目」的流程里补一步检查。有相近的条目，就合并进去，不另起一条。
3. **确实是新原则，才新加一条。**

**`沉淀/` 只写以后照着做的规则，不写事件记录。** 日期、哪篇稿子、哪一句改成了什么，都不往 `沉淀/` 里记：这些会越积越长，每次读都浪费额度，还会把规则淹没。历史在产出的各个版本里。需要例子时，在规则下面附「反例 → 正例」，一条规则最多一两组。

- 提议时用一句话：「这条建议写进 X：……，要写吗？」用户确认后再写，写完告诉用户写在了哪里。（不可覆盖）
- 提议时说清楚是新加、合并进哪一条，还是只补例子。
- 几条要点可以一起问，但每条都要写清楚内容和要写到哪里。
- 当场提议，不要等到最后再统一整理。
- 收尾时的沉淀检查见第五节。
- 写之前先看文件里有没有相同或冲突的条目：有就更新原条目，不要重复追加。
- 在 `沉淀/` 里**新建**文件时，同时在 `AGENTS.md` 的「做事之前先读」里登记一行：文件名，加一句说明它管什么、什么时候读。
- `沉淀/` 里某个文件明显变长、出现重复、或者混进了事件记录时，提议整理一次：把只针对单个点的条目提炼、合并成原则，把事件记录删掉或改成例子。整理也要先问用户。

### 四、进度

`进度.md` 由 Agent 维护，用户不需要动手记。

- **什么时候建条目**：用户提的事在当前回合做不完，比如交给别的 Agent 或队列执行、要等明天、或者分好几步完成，就建一条。当场就能做完的事不记。
- **怎么写**：用用户自己的话写这件事，写清楚结果在哪里。
- **在哪些节点更新**（谁做这一步，谁就更新）：

| 节点 | 状态改为 |
|---|---|
| 用户提出这件事，当前回合做不完 | 已收到 |
| 开始做，或者交给别的 Agent 或队列 | 处理中 |
| 做完、自查通过，可以给用户看了 | 待你验收（写清楚去哪里看、应该看到什么） |
| 卡住了，需要用户拍板或授权 | 需要你决定（写清楚要决定什么） |
| 用户说通过 | 已完成 |
| 用户说不通过 | 处理中（写上原因） |

- 用户问「做到哪了」时，读 `进度.md`，用一张简短的表回答。
- 用户要可视化看板时，按 `机制/可视化说明.md` 来做。`进度.md` 始终是唯一的数据来源，看板只读不写。

### 五、收尾

任何任务（写稿、开发功能、修 bug 等）最后都要验收。收尾不一定由用户发起，Agent 要主动判断并推进。

**两种触发方式**

| 触发方式 | 什么情况 | 怎么做 |
|---|---|---|
| 用户发起 | 用户用任何说法表示可以了，比如「行了」「通过」「就这样」「定稿」 | 直接进入收尾 |
| Agent 判断 | 满足任意一条：约定的验收标准都已满足、自查也通过；最新版已经交给用户，用户没有再提修改意见；`进度.md` 里的条目已经到了「待你验收」 | 说出判断依据，问用户：「我看这件事已经可以验收了，你确认通过吗？」用户确认后再进入收尾 |

最终算不算通过，由用户确认。Agent 只负责判断和提议。

**收尾做这几件事，按顺序：**

1. **沉淀检查**：列出这次对话里还没写进文件的要点，一次性问用户要不要写（写之前必须先问，不可覆盖）。
2. **项目自己的收尾步骤**：如果「本项目」里规定了完成后要做的事，比如把成果挪到某个文件夹，就照做。
3. **更新进度**：如果 `进度.md` 里有对应条目，改成「已完成」。
4. **归档对话**：问用户「要归档这个对话吗？」。你所在的工具能归档当前对话的，用户同意后就帮他归档；不能的，提醒用户自己归档。归档后这个对话就结束了，所以这一步一定放在最后。
