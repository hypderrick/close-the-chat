# 沉淀说明

给 Agent 看。用户纠正、补充或者做出选择，而且是「以后都要这样」时读。写之前一定先问用户（不可覆盖）。

## 写到哪里

| 类型 | 写到哪里 |
|---|---|
| 只针对这一次 | 不沉淀，在当前产出里改掉即可 |
| 以后的做事流程 | `AGENTS.md` 的「本项目」一节 |
| 以后不能怎样、必须怎样 | `沉淀/规则.md` |
| 风格、语气、偏好 | `沉淀/风格.md` |
| 否决了某个方案，以及原因 | `沉淀/规则.md` 里的「已否决」一节 |
| 项目要用的事实、资料（数字、链接、发布状态等） | 项目的资料文件（如素材库），不是 `沉淀/`，也不是 `进度.md` |

## 提议之前，按顺序想三步

1. **往上提炼**：这次纠正背后的通用原则是什么？要沉淀的是原则，不是这一个句子、这一个词。比如用户把一句病句改了，原则可能是「交稿前通读一遍」，而不是「这句不要这样写」。
2. **查现有条目**：现有规则或流程已经覆盖了这个原则，就说明是没执行，不新加条目。可以做的是：在原条目下补一个例子；或者问题出在漏了自查，就在「本项目」的流程里补一步检查。有相近的条目，就合并进去，不另起一条。
3. **确实是新原则，才新加一条。**

## 只写规则，不写事件记录

日期、哪篇稿子、哪一句改成了什么，都不往 `沉淀/` 里记：这些会越积越长，每次读都浪费额度，还会把规则淹没。历史在产出的各个版本里。需要例子时，在规则下面附「反例 → 正例」，一条规则最多一两组。

## 怎么提议

- 用一句话：「这条建议写进 X：……，要写吗？」用户确认后再写，写完告诉用户写在了哪里。
- 说清楚是新加、合并进哪一条，还是只补例子。
- 几条要点可以一起问，但每条都要写清楚内容和要写到哪里。
- 当场提议，不要攒着。拿不准是不是「以后都要这样」，也当场问用户；用户说先不写，就不写，不要另找地方记下来等以后再提（比如在 `进度.md` 里记「待观察」）。
- 写之前先看文件里有没有相同或冲突的条目：有就更新原条目，不要重复追加。

## 新建文件和整理

- 在 `沉淀/` 里**新建**文件时，同时在 `AGENTS.md` 的「做事之前先读」里登记一行：文件名、管什么、什么时候读（每件事都用得上的标「每次」，只对某类任务有用的写明哪类任务，不写「必要时」）。
- 不要预先拆文件。一个标「每次」的文件里，出现一大块只对某类任务有用的内容时，才提议把它拆出来，登记成到那类任务再读。
- 整理：把只针对单个点的条目提炼、合并成原则，把事件记录删掉或改成例子。整理也要先问用户。检查的时机见 `机制/收尾说明.md`。
